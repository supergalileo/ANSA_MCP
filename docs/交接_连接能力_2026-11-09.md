## 一、为什么要做这件事

上一阶段交付的是 **402 个互相独立的零件级网格**。它们：

- 节点不共享（每件单独 `base.Open` 一个新库）
- 零件之间没有任何连接单元
- 因此**无法直接提交整车求解**——一跑就散架（无约束的刚体模态）

这是当前能力和「能算整车」之间唯一的关键缺口。补齐它，工具链才从「零件级」升到「总成级」。

**目标定义（先对齐，别急着写代码）**：给定 402 个已交付的 `.ansa` 和一套连接位置数据，产出一份**可提交求解**的整车模型，其中：

1. 所有零件被搬进同一个库里、按装配位置摆好
2. 每个焊点/胶接位置都有对应的连接单元
3. 连接单元的两端节点实实在在挂在两层壳上（不是悬空）
4. 导出 `.nas` 后能用求解器跑通，刚体模态数 = 6

第 4 条是验收标准。前三条都可能"看起来成功"而实际不通。

## 三、技术路线（三条路，建议按顺序试）

### 路线 A：几何最近邻自动连接 —— 最快出结果，最不可靠

**做法**：焊接球体的中心坐标 → 在每个球体半径 R 内的所有壳单元节点里，找属于两个不同零件的最近节点对 → 建 `RBE3` 或 `CWELD`。

**优点**：不需要连接清单，纯几何，一天能写出原型。

**致命问题（必须承认）**：
- 相邻但**不连接**的零件会被误连（例如间隙 0.5 mm 的两块板）
- 搭接区（三层板）判定不了哪两层是一对
- 容差 R 是全模型一个常数，但实际间隙分布很宽
- **错误连接比没有连接更糟**：模型看着能跑，刚度是错的，而且没人会发现

**适用场景**：只有几何、没有清单，且只做趋势分析（模态频率量级、传力路径）。
**不适用于**：任何要出报告的强度/刚度分析。

### 路线 B：读连接清单 + 坐标匹配 —— 推荐的中间态

**前提**：2.3 的第 3 个问题答案是「有表格」。

**做法**：
```
连接清单.csv（点号, 坐标xyz, 零件1, 零件2, 类型）
   ↓
脚本读取 → 按坐标在 402 个网格里做最近搜索
   ↓
找到零件1 上的节点 A、零件2 上的节点 B（距离 < tol）
   ↓
建 RBE3(A 主节点, B 从节点集) 或 CWELD
   ↓
记录：匹配成功的点数 / 未匹配点数 / 距离分布
```

**关键设计点**：
- **必须输出匹配报告**：每个焊点的实际间距、用了哪两个节点、是否超过容差。
  4240 个焊点里如果有 200 个间距 > 3 mm，说明零件位置对不上，先解决几何问题。
- **不要静默补**：匹配不到就报出来，不要"就近连一个"。
- 三层板：一个点要连三对，清单里应有 3 行。

### 路线 C：用 ANSA 自带连接功能 —— 最靠谱但要逆向 API

**思路**：ANSA 的 `Deck > Connections` 模块本身就有完整能力（Spotwelds、Seam welds、Adhesive、Bolts），
GUI 上做的东西背后都是 Python API。

**要先摸清的 API**（`ansa_api_search` 查，或直接 `dir()`）：
- `connections` 模块是否存在（`from ansa import connections`）
- `base.CollectEntities(deck, None, "CONNECTIONS")` 返回什么
- 焊接单元的卡类型：NASTRAN deck 下是 `CWELD` / `CROD` / `RBE3`？

**风险**：`ansa-api-verified.md` 里没有任何 connections 的记录，等于从零开始。
建议先花半天做**只读勘察**：打开一个手工做过连接的 ANSA 库，用
`base.CollectEntities` + `ent.card_fields(deck)` 把所有实体类型列一遍，看清楚 ANSA 是怎么存的。

**优点**：一旦走通，连接质量就是 ANSA 官方水平，不用自己调容差。
**缺点**：如果 connections 模块在 batch 模式下不可用（很可能），就得退回 A/B。

### 我的判断

**先花半天做 2.3 的勘察，再决定走 B 还是 C。**

- 有清单 → B（可控、可验证）
- 没清单 + ANSA connections 可用 → C
- 没清单 + connections 不可用 → A，但**必须在报告里写死「仅供趋势分析」**

## 四、必须先想清楚的五个坑

### 坑 1：零件坐标怎么对齐

402 个 `.ansa` 是**各自从 CATPart 单独导入**的。CATPart 里可能有装配变换矩阵，
`base.Open` 是按 CATIA 里的绝对坐标还是局部坐标导入？**没有验证过。**

如果坐标没对齐，所有零件会堆在原点，连接全部失败。
→ 验证方法：取两个已知相邻的零件，导入后看 `base.BoundBox` 是否相邻。

### 坑 2：单元规模会翻几倍

402 件 = 174 万壳单元。搬进一个库以后：
- 内存：单库 174 万单元，ANSA 大约要 3–6 GB（估算，未实测）
- 导出 `.nas`：可能 2–3 GB 文本
- 求解：这个规模必须上集群

**先在 10 件零件的子集上验证全流程**，不要一上来就整车。

### 坑 3：`RBE3` vs `CWELD` vs `CROD` 不是等价选择

| 类型 | 语义 | 适用 |
|---|---|---|
| `RBE3` | 主节点位移 = 从节点加权平均 | 焊接/胶接的常用替代，柔性连接 |
| `CWELD` | Nastran 专用焊接单元 | 更接近真实焊点，但需要 `PWELD` 属性 |
| `CROD` | 刚性杆 | 只适合粗算，会引入虚假刚度 |

用 `RBE3` 最省事，但**必须在报告里写明这是等效处理**，不是真焊点。
真正的焊点直径、材料、失效都需要 `CWELD` + 实验数据。

### 坑 4：三层板 / 缝焊 / 胶接是三种不同问题

- **点焊**：点对点，最简单
- **缝焊**（`ADHESIVE` 41 MB 那个很可能是）：沿路径连续连接，要么建成一排 `RBE3`，要么建实体胶层
- **三层板**：一个点连三对，容易漏

不要用一个脚本套所有情况。先只做**点焊**，跑通再扩。

### 坑 5：验收标准必须是可计算的

「看起来连上了」不算。验收要能跑出数来：

| 验收项 | 判据 |
|---|---|
| 连接单元数 | = 连接清单行数（误差 0） |
| 每个连接两端都有节点 | 0 个悬空 |
| 求解器跑通 | 自由模态，**刚体模态数 = 6**（多于 6 说明还有零件没连上） |
| 最低弹性模态频率 | 与手工模型对比，差 < 15% |

**「刚体模态数 = 6」是最硬的指标。** 它是 1 行输出，但能一次抓住所有漏连。

## 五、代码放在哪

### 5.1 目录结构建议

```
ANSA_MCP/
└── skills/
    ├── ansa-midsurface-mesh/        ← 现有，不动
    └── ansa-connection/             ← 新建
        ├── SKILL.md                 ← 什么时候用、什么时候不用
        ├── references/
        │   ├── ansa-connection-api.md   ← 和 ansa-api-verified.md 同样风格
        │   └── field-notes.md           ← 踩坑记录
        └── scripts/
            ├── inspect_connection_data.py   ← 第一步：勘察（只读）
            ├── assemble_parts.py            ← 把 402 个 .ansa 合进一个库
            ├── connect_spots.py             ← 点焊
            ├── connect_adhesive.py          ← 胶接（后做）
            └── verify_connections.py        ← 验收：数连接、查悬空、跑模态
```

**为什么单独开一个 skill**：中面网格和连接建模是两件事，输入不同、风险不同、验收不同。
塞进一个 skill 会让 description 变得又长又糊，agent 触发不准。

### 5.2 复用现有能力

- `inspect_model.py`——只读勘察，可以直接改造成 `inspect_connection_data.py`
- `parallel_batch.py` 的进程管理、超时、watchdog——整车导入可能需要，但逻辑不同，别硬套
- `make_summary.py` 的异常清单思路——连接匹配报告照抄这个格式

### 5.3 命名约定要继承

现有约定：`B0029_A0072600089.CATPart → A0072600089`
连接点命名建议：`SPOT_<点号>_<零件1>_<零件2>`，或者直接用清单里的原始点号。
**注意**：property 名不能有空格和分号（会破坏 Abaqus ELSET），这条同样适用。

## 七、别踩的坑（上一阶段的血泪，同样适用）

1. **别信"看起来成功"**。上一阶段 540 件交付了 452 个 `.ansa`，清单每行路径都存在，零报错——
   因为每行指向的是兄弟件的文件。**验收必须数磁盘上的真实文件**，不是数清单行。
2. **别在现有目录上就地重跑**。宿主的批量删除守护阈值 50/次，超了直接杀进程，
   worker 只留一行 `[safe-delete]`，没有 traceback。写新目录 + `os.replace`。
3. **别只报成功数**。异常清单是交付的一部分，跳过一件必须能看见。连接项目同理：
   **每个没匹配上的焊点都要出现在报告里**。
4. **改完脚本必须真跑一遍最小样例**。参数名错误能通过编译，但运行时立刻崩溃。
